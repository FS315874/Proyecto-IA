# Decisión de arquitectura de v0.13

## Alcance y privacidad

v0.13 transforma una frase hablada en el mismo texto que recibe el servicio local. Se
eligió `System.Speech` antes que una API externa o un modelo local adicional porque ya
forma parte del stack Windows comprobado, no necesita descargar paquetes y mantiene el
audio en el equipo.

No hay escucha permanente. El usuario pulsa `Hablar una frase`; el helper usa el
micrófono predeterminado por hasta diez segundos y termina al reconocer o agotar el
timeout. No crea WAV, caché de audio, request de red o log de transcripción.

## Backend y contrato

`recognize_speech.ps1` es código fijo incluido como package data. Python lo ejecuta con
Windows PowerShell, `-File`, argumentos de cultura allowlisted, `shell=False` y ventana
oculta. No usa `-Command` ni incorpora texto del usuario. Selecciona la cultura pedida
y, si falta, el primer reconocedor español instalado.

El único resultado permitido es JSON v1 con estado, texto, confianza, cultura y
latencias. Python limita stdout, valida campos exactos, normaliza hasta 500 caracteres
y convierte confianza baja en ambigüedad. Timeout, cancelación o contrato inválido
terminan el proceso y descartan cualquier texto parcial.

## Flujo de interfaz

```text
gesto explícito -> VoiceController -> WindowsSpeechBackend
    -> transcripción editable -> DesktopAgentService
    -> LocalAgentController -> CommandProcessor -> ActionExecutor
```

La UI nunca envía automáticamente una transcripción ordinaria. El usuario puede
corregirla y debe pulsar `Enviar transcripción`. El servicio marca el origen como voz,
pero reutiliza validación, catálogo, presupuesto y herramientas existentes.
Si el fallback de texto con IA está habilitado, el texto enviado puede seguir esa
configuración y costo; el audio nunca sale del reconocedor local.

Una confirmación sensible sigue exigiendo su botón: el servicio rechaza transcripciones
mientras hay una confirmación pendiente. Sólo tres frases exactas de emergencia se
ejecutan sin revisión y únicamente cancelan o detienen trabajo.

## Observabilidad y validación

Los eventos registran ID, estado, cultura, confianza y latencias de captura,
transcripción y total. No registran texto, audio, stdout, stderr o errores internos.
Interpretación y ejecución mantienen sus métricas separadas en el servicio.

Se validaron:

- captura solo tras gesto y rechazo de una segunda captura simultánea;
- cancelación y cierre del worker;
- transcripción válida, ambigua, vacía, larga y con esquema inválido;
- silencio, helper ausente, timeout y fallo inesperado redactado;
- comando fijo sin `-Command`, shell, texto privado o red;
- edición antes de enviar y separación de confirmaciones;
- cancelación verbal exacta y rechazo de frases parecidas;
- 14 pruebas nuevas, suite de 304 y QA Tk real con backend falso;
- disponibilidad real de un reconocedor `es-ES`, sin activar el micrófono.

## Limitaciones

- la calidad depende del reconocedor de voz instalado en Windows;
- `System.Speech` informa reconocimiento combinado; transcripción adicional puede ser
  cero porque ocurre dentro de la misma llamada;
- no se realizó una prueba real de micrófono para no capturar audio privado;
- no hay streaming, dictado continuo, palabra de activación o reconocimiento externo;
- la frase verbal de emergencia puede detener trabajo, pero nunca aprobar o ampliar
  una acción.
