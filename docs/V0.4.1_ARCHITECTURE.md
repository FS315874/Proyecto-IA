# Decisión de arquitectura de v0.4.1

## Estado

- Decisión: aprobada el 2026-08-25.
- Opción: interfaz nativa con Tkinter/ttk.
- Versión: `0.4.1`.

## Problema

La CLI reconstruía el proceso en cada ejecución de una sola orden y Codex seguía
siendo el intermediario práctico. La versión necesita una entrada local persistente
sin adelantar voz, acceso remoto, visión ni automatización general.

## Alternativas consideradas

### Interfaz nativa

Ventajas:

- no abre un socket ni crea una API local;
- comunicación directa y estructurada dentro del proceso;
- cierre y propiedad de recursos inequívocos;
- Tkinter/ttk forma parte de una instalación completa de CPython.

Costos:

- la distribución embebida de Python para Windows excluye Tcl/Tk;
- la UI tiene una estética más limitada;
- el event loop no debe ejecutar tareas bloqueantes.

### Interfaz web local

Ventajas:

- mayor flexibilidad visual;
- base reutilizable para una interfaz remota futura.

Costos:

- requiere un servidor, puerto, ciclo de vida y protección contra solicitudes de
  otros orígenes;
- la biblioteca estándar `http.server` solo ofrece controles de seguridad básicos;
- adelanta problemas de acceso remoto que pertenecen a v0.14.

## Arquitectura adoptada

```text
Tkinter/ttk (hilo principal)
        |
        | órdenes y eventos estructurados
        v
LocalAgentController (cola + worker único)
        |
        v
CommandProcessor
        |
        +--> HybridInterpreter
        +--> ActionExecutor
        +--> herramientas registradas
        +--> sesión Playwright persistente
```

La ventana nunca invoca herramientas. `CommandProcessor` comparte el flujo de la CLI
y conserva la validación del `ActionExecutor`. El worker es el único propietario de
Playwright, por lo que creación, uso y cierre ocurren en el mismo hilo.

## Ciclo de vida

- El proceso Python es propietario del núcleo y de la ventana.
- Un lock por usuario impide dos consolas simultáneas.
- Las órdenes tienen identificador local, longitud máxima y ejecución serial.
- Detener se procesa en el hilo propietario al terminar la operación acotada actual.
- Emergencia cancela órdenes pendientes y prioriza la detención.
- Cerrar cancela pendientes, detiene reproducción, cierra el worker y libera el lock.

No se terminan hilos de forma forzada. Una operación bloqueante existente solo puede
cancelarse en el siguiente límite seguro; los timeouts del backend siguen siendo la
barrera durante esa operación.

## Observabilidad

Cada resultado conserva:

- etapa actual;
- identificador no sensible;
- tiempo en cola, tiempo de ejecución y total;
- resultado estructurado;
- snapshot mensual agregado de tokens, costo y presupuesto cuando existe.

La orden no se agrega al log persistente y la UI no guarda historial en disco.

## Runtime comprobado

La instalación embebida de CPython 3.13.15 no incluía `tkinter`, tal como documenta
Python. Se usó el instalador oficial de 64 bits, se comprobó su SHA-256 y se instaló
para el usuario sin añadir PATH, launcher ni accesos directos. Tk 8.6 quedó disponible.

Fuentes:

- https://docs.python.org/3.13/using/windows.html#the-embeddable-package
- https://docs.python.org/3.13/library/tkinter.html#threading-model
- https://docs.python.org/3.13/library/http.server.html

## Validación

- suite de 154 pruebas locales;
- serialización y reutilización del worker;
- rechazo de entradas vacías y sobredimensionadas;
- stop en el mismo hilo propietario;
- cancelación de pendientes por emergencia;
- cierre idempotente y lock de instancia;
- formato de uso y latencia;
- smoke real de creación y cierre de una ventana Tkinter.

La interacción visible automatizada quedó omitida porque el permiso del controlador
de Windows expiró. La ventana abierta para esa comprobación se cerró normalmente y no
se ejecutaron órdenes ni efectos externos.
