# Propuesta de arquitectura para v0.4 — Browser Automation

> Estado: v0.4 completada mediante WEB-01 a WEB-08 el 2026-08-25. La CLI expone el
> flujo verificado con sesión persistente, detención explícita y errores estructurados.

## 1. Objetivo y límite

v0.4 agregará un flujo web acotado y verificable mediante DOM. La demostración
candidata buscará contenido en YouTube, seleccionará un resultado permitido e
iniciará la reproducción sin visión, mouse ni teclado.

La versión conservará estas fronteras:

- el modelo no produce selectores, JavaScript, URLs ni comandos de navegador;
- el núcleo valida una acción estructurada antes de invocar una herramienta;
- el adaptador expone operaciones semánticas y reemplazables en tests;
- no se reutilizan cookies, sesiones, extensiones ni el perfil personal del usuario;
- una acción no se considera exitosa hasta verificar un resultado observable;
- no se incorporan todavía planes de varios pasos ni control visual.

## 2. Alternativas evaluadas

| Alternativa | Ventajas | Riesgos | Decisión |
| --- | --- | --- | --- |
| Playwright con Chromium administrado | Auto-wait, locators, contextos aislados y binario ligado a la biblioteca | Descarga grande y acoplamiento de versiones | Elegida |
| Playwright con Chrome instalado y perfil separado | Menor descarga y codecs propietarios | Menor reproducibilidad; políticas y actualización local | Fallback futuro |
| Playwright conectado a Chrome personal | Conserva login y pestañas | Expone datos privados, estado ambiguo y perfil principal no soportado | Rechazada |
| Selenium WebDriver | Estándar maduro y multiplataforma | Agrega driver/manager y más piezas para este flujo acotado | Rechazada |
| Chrome DevTools Protocol directo | Acceso Chromium sin una capa adicional | Solo Chromium y menor fidelidad de conexión | Rechazada |

## 3. Dependencia seleccionada

Se fija `playwright==1.62.0` porque cada versión de Playwright requiere binarios de
navegador concretos. La metadata oficial declara Python >=3.10, licencia Apache-2.0
y soporte para Python 3.13. La API síncrona encaja con la CLI actual y evita introducir
un event loop antes de necesitar concurrencia.

Referencias oficiales:

- [paquete y metadata en PyPI](https://pypi.org/project/playwright/);
- [instalación y gestión de navegadores](https://playwright.dev/python/docs/browsers);
- [aislamiento mediante BrowserContext](https://playwright.dev/python/docs/browser-contexts);
- [límites de perfiles persistentes y conexión CDP](https://playwright.dev/python/docs/api/class-browsertype).

El comando aprobado instala únicamente la familia Chromium requerida:

```powershell
python -m playwright install chromium
```

La instalación comprobada descargó:

- Chrome for Testing 151.0.7922.34 para ejecución visible;
- Chromium Headless Shell de la misma revisión;
- FFmpeg y el verificador de dependencias de Windows.

No descargó Firefox ni WebKit. Los archivos extraídos ocuparon aproximadamente
701 MiB en `%LOCALAPPDATA%\ms-playwright`. La cifra puede cambiar entre versiones.

## 4. Navegador y aislamiento aprobados

El primer flujo usará Chromium administrado y un `BrowserContext` temporal no
persistente. Cada ejecución comenzará sin cookies ni almacenamiento previo y cerrará
contexto y navegador aun cuando falle.

La demostración audible se ejecutará en modo visible. El modo headless se reservará
para pruebas sin audio, porque Chromium lo inicia silenciado. Si una prueba observable
demuestra una limitación de codecs, se podrá evaluar Chrome estable mediante el canal
oficial de Playwright y otro perfil aislado; esa alternativa no habilita el perfil
personal.

## 5. Política inicial de seguridad

Los próximos pasos deberán conservar:

- destinos y orígenes permitidos definidos localmente;
- consultas tratadas como datos, nunca como URL, selector o código;
- descargas, permisos y acceso a archivos deshabilitados salvo decisión posterior;
- límites de páginas, acciones, duración y reintentos;
- cancelación y cierre garantizado de recursos;
- logs de operación, destino canónico, duración y resultado sin contenido privado;
- fallo seguro ante popups, consentimiento desconocido, ausencia de resultados o DOM
  incompatible.

Para reproducción, la verificación mínima futura será: URL o título esperado,
`paused=false`, `muted=false`, volumen mayor que cero cuando esté disponible y avance
de `currentTime` durante una ventana acotada. La salida de Windows o los parlantes no
son observables mediante DOM y deberán declararse como límite.

## 6. Riesgos y mantenimiento

- Playwright y su navegador se actualizan conjuntamente; una actualización exige
  revisar release notes, reinstalar Chromium y repetir integración.
- YouTube puede variar DOM, consentimiento, anuncios, disponibilidad regional y
  políticas de autoplay.
- Un clic o una URL `/watch` no prueban reproducción ni audio.
- El navegador agrega aproximadamente 701 MiB en la instalación observada.
- La suite normal debe seguir usando dobles; un E2E real será opcional, separado y
  requerirá autorización de red y efecto visible.

## 7. Contrato implementado en WEB-02

`desktop_agent/browser_contract.py` separa el dominio del futuro backend Playwright.
La interfaz pública `BrowserAdapter` admite únicamente estas operaciones:

- abrir un sitio mediante su clave canónica;
- buscar texto tratado como datos;
- seleccionar el primer resultado según la política local;
- iniciar y observar reproducción;
- cerrar recursos.

No acepta URL, selector, JavaScript, coordenadas, ruta, perfil ni argumento de
lanzamiento. Los destinos se resuelven con el catálogo local y las consultas se
normalizan y limitan a 200 caracteres.

`BrowserLimits` fija tiempos máximos de navegación, operación, verificación y flujo.
`PageSnapshot`, `SearchSnapshot`, `PlaybackSnapshot`, `BrowserError` y
`BrowserStepResult` validan la observación antes de que otra capa pueda usarla. Los
efectos quedan detrás de puertos inyectables para navegador, contexto y página; reloj
y espera también son reemplazables.

WEB-02 agregó 17 pruebas unitarias. Todas usan dobles, verifican invariantes y
confirman que la firma pública no expone entradas peligrosas. La suite completa quedó
en 97 pruebas sin red ni ventanas.

## 8. Herramienta segura implementada en WEB-03

`desktop_agent/browser_adapter.py` implementa `SafeBrowserAdapter` como una máquina
de estados sobre los puertos de WEB-02. `BrowserSecurityPolicy` restringe la versión
a YouTube, una sola página, contexto no persistente, sin extensiones, descargas ni
acceso a archivos. Las operaciones fuera de orden fallan antes de alcanzar el backend
y los fallos externos se convierten en errores estructurados sin registrar detalles
privados.

`desktop_agent/tools/browser_automation.py` agrega una herramienta invocable y
registrable en `ActionExecutor`. La herramienta recibe solo una clave canónica,
registra intención, destino, duración y resultado, y garantiza el intento de cierre
del contexto y del navegador. No está registrada en la CLI y no inicia Playwright.

WEB-03 agregó 16 pruebas con un backend falso. Comprueban allowlist, orden, timeouts,
ausencia de resultados, redacción, cierre idempotente, cierre parcial y registro en el
ejecutor. La suite completa quedó en 113 pruebas sin red, audio ni ventanas.

## 9. Flujo vertical implementado en WEB-04

`desktop_agent/playwright_backend.py` encapsula los selectores fijos de YouTube y la
creación diferida de Chromium. La fábrica usa un contexto temporal, rechaza descargas,
no concede permisos, bloquea service workers y no recibe perfiles, extensiones,
argumentos ni rutas externas.

`YouTubePlaywrightPage` escribe la consulta normalizada como datos, espera el DOM de
resultados y solo acepta enlaces `/watch` con un identificador localmente validado.
Reconstruye una URL canónica que elimina parámetros adicionales antes de navegar. Los
selectores ausentes, links externos, consentimiento, cero resultados y timeouts se
convierten en condiciones conocidas; ningún detalle de Playwright llega a los logs.

WEB-04 estableció cuatro pasos: abrir YouTube, buscar,
seleccionar el primer video permitido, iniciar y quitar el silencio. Se detiene
en el primer fallo, no registra la consulta y siempre intenta cerrar los recursos.
La consulta inválida se rechaza antes de construir el navegador.

WEB-04 agregó 14 pruebas y llevó la suite a 127 casos. Todos usan páginas, navegador,
contexto y runtime falsos; no hubo red, audio ni ventanas. El estado inicial del
reproductor se observa, pero el avance temporal todavía no se verifica.

## 10. Verificación implementada en WEB-05

`BrowserAdapter.verify_playback` agrega un quinto paso semántico antes del cierre. La
operación observa el reproductor, espera la ventana local de un segundo y vuelve a
observarlo. Exige el mismo identificador `/watch` en el host permitido,
`paused=false`, `muted=false`, volumen mayor que cero cuando está disponible y al
menos 0,1 segundos de avance en `currentTime`.

La espera y el reloj siguen siendo inyectables. Un cambio de video, host externo,
pausa, silencio, volumen cero o progreso insuficiente produce
`PLAYBACK_NOT_CONFIRMED`; el flujo no informa éxito y aun así cierra todos los
recursos. La consulta, URL y título observados no se incorporan a los logs.

WEB-05 agregó cuatro pruebas y llevó la suite a 131 casos. La verificación fue
simulada sin esperar tiempo real, usar red, abrir Chromium ni comprobar la salida de
Windows o los parlantes.

## 11. Matriz de pruebas consolidada en WEB-06

La suite separa cuatro niveles reproducibles:

- contrato: tipos, firmas, límites y resultados por operación;
- adaptador: estados, allowlist, errores, cierre y verificación temporal;
- backend: selectores fijos, navegación canónica, aislamiento y limpieza;
- integración local: `ActionExecutor`, herramienta, fábrica, adaptador y backend
  compuestos con un runtime Playwright falso.

La integración positiva recorre el flujo completo hasta `VERIFY_PLAYBACK`; la negativa
simula consentimiento y comprueba fallo seguro y cierre. WEB-06 hizo inyectables el
reloj y la espera desde la fábrica, agregó dos pruebas y llevó la suite a 133 casos.
No hubo proceso Chromium, espera real, red ni datos externos.

El E2E externo continúa siendo opcional porque depende del DOM, disponibilidad,
consentimiento y red de YouTube. No forma parte de la suite normal ni se ejecutó en
WEB-06.

## 12. Resultado de WEB-07

El runner manual separado `scripts/web07_manual_check.py` usa casos fijos o una
consulta pública interactiva normalizada, Chromium visible y un contexto efímero.
Mide interpretación, arranque, navegación y total sin incorporar las consultas a los
logs. La interpretación figura como no aplicable porque la automatización todavía no
está registrada en la CLI.

La ejecución autorizada del 2026-08-25 produjo estos resultados:

- consulta válida: éxito de las cinco operaciones y cierre; arranque 1,47 s,
  navegación y verificación 7,15 s, total 9,01 s;
- consulta interactiva elegida por el usuario: segundo éxito; arranque 3,83 s,
  navegación y verificación 7,10 s, total 11,38 s;
- sin resultados: no reproducido; YouTube devolvió un resultado para una cadena
  aleatoria y el runner marcó correctamente que no observó el resultado esperado;
- cancelación: `Ctrl+C` interrumpió la espera manual, pero `close()` devolvió
  `backend_failure`;
- contenido no disponible: no ejecutable mediante el contrato actual, que sólo
  acepta una consulta y elige automáticamente el primer resultado permitido.

El DOM confirmó reproducción sin mute y avance de `currentTime`; no confirma la
salida física de audio.

La corrección posterior mantiene el adaptador verificado dentro de
`YouTubePlaybackTool` y agrega `stop()` como cierre explícito e idempotente. Los fallos
siguen cerrándose inmediatamente; una consulta inválida no interrumpe la sesión activa
y un reemplazo sólo puede comenzar después de cerrar la anterior. El runner espera
Enter en lugar de enviar `Ctrl+C` al runtime. Tres pruebas nuevas llevan la suite a
136 casos.

La repetición real mantuvo la reproducción durante 8 min 43 s y cerró limpiamente en
0,29 s. Los negativos se comprobaron sin forzar el servicio externo: cero resultados
usa su marcador DOM y contenido no disponible produce el nuevo error estructurado
`CONTENT_UNAVAILABLE` cuando aparece el marcador fijo del reproductor. Cuatro pruebas
nuevas llevan la suite a 137 casos. WEB-07 quedó completado sin debilitar la interfaz
pública y habilitó el cierre integral de WEB-08.

## 13. Cierre de WEB-08 y v0.4

La automatización deja de ser sólo una composición o runner de prueba. La CLI registra
un único `YouTubePlaybackTool` como `play_youtube` y su cierre como `stop_youtube`.
La construcción del controlador no inicia Playwright; la fábrica se evalúa recién al
recibir una orden de reproducción.

El parser determinista admite formas acotadas con la consulta antes o después de
`en youtube`. Preserva mayúsculas y acentos, colapsa espacios y aplica el límite local
de 200 caracteres. La consulta sólo llega al parámetro semántico `query`; no se usa
como comando, URL, selector ni script, no se envía al fallback y no aparece en logs.

En modo interactivo la herramienta conserva la sesión entre órdenes y permite
reemplazarla o detenerla. `salir` intenta cerrar cualquier sesión activa. Una ejecución
de una sola orden espera Enter y después detiene, de modo que el proceso siga siendo
el dueño de Chromium. No se adoptó un perfil persistente ni Chrome personal.

Siete pruebas nuevas verifican parsing, registro explícito, bypass de IA, espera de una
sola orden, versión del banner y limpieza de salida. La suite completa contiene 144
casos sin red ni ventanas; la evidencia real de WEB-07 cubre reproducción audible y
cierre controlado. El paquete y el módulo declaran `0.4.0`.

Limitaciones que permanecen:

- el DOM no demuestra la salida física de audio;
- los selectores dependen del sitio externo;
- `Ctrl+C` puede afectar al proceso Playwright en Windows; se prefieren
  `detener youtube`, `salir` o Enter;
- no existe aún una interfaz gráfica, voz, acceso remoto, screenshots ni control
  general de mouse o teclado.

El incremento siguiente acordado es v0.4.1 — Local Control Console. Separará la vida
del agente de la conversación con Codex mediante un proceso local persistente y una
interfaz mínima. La elección tecnológica queda como checkpoint de decisión.
