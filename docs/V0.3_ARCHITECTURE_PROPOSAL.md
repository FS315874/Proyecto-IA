# Propuesta de arquitectura para v0.3 — Natural Language

> Estado: propuesta de diseño. v0.3 no está implementada y este documento no adopta
> un proveedor, modelo, SDK ni dependencia.

## 1. Objetivo

v0.3 permitiría interpretar variantes de lenguaje natural para las capacidades que
el agente ya tenga autorizadas. Por ejemplo:

```text
poneme youtube
iniciá el editor de código
quiero usar la calculadora
```

El resultado seguiría siendo una única acción explícita y validada. Esta versión no
amplía qué puede hacer el equipo; solo propone una forma más flexible de seleccionar
acciones existentes.

## 2. Estado de partida comprobado

v0.2 usa un flujo completamente determinista:

```text
CLI -> parse_command -> Action -> ActionExecutor -> herramienta registrada
```

El repositorio ya contiene:

- `Action`, `Intent`, `RiskLevel` y `requires_confirmation`;
- un catálogo cerrado de sitios y aplicaciones;
- las herramientas `open_url` y `open_application`;
- un ejecutor que rechaza riesgos no seguros y herramientas desconocidas;
- dependencias inyectables para probar efectos sin abrir aplicaciones reales;
- una suite basada en `unittest` y sin paquetes externos.

Estas fronteras deben conservarse. El futuro intérprete no reemplazará al ejecutor,
al catálogo ni a las validaciones existentes.

## 3. Alcance propuesto

v0.3 incluiría solamente:

- interpretación de expresiones alternativas para intents existentes;
- salida estructurada de una sola propuesta;
- validación local de estructura, intent y destino;
- fallback al mensaje de comando no soportado ante cualquier ambigüedad o fallo;
- métricas básicas de uso, duración y resultado de la interpretación;
- pruebas con un proveedor falso, sin llamadas reales en la suite predeterminada.

Queda fuera:

- agregar herramientas o destinos por decisión del modelo;
- URLs, ejecutables, rutas o argumentos arbitrarios;
- planes o tareas de varios pasos;
- reintentos autónomos;
- Playwright, screenshots, visión, mouse o teclado;
- memoria, persistencia o envío de contexto del escritorio;
- selección automática de acciones `CAUTION` o `DANGEROUS`;
- confirmación de acciones sensibles;
- implementación de un proveedor o SDK dentro de esta preparación.

## 4. Opciones consideradas

### A. Ampliar únicamente el parser determinista

Ventajas:

- sin costo, red ni dependencia externa;
- comportamiento rápido, privado y reproducible;
- pruebas sencillas.

Limitaciones:

- cada nueva formulación requiere reglas o alias;
- escala mal ante expresiones ambiguas o variadas.

Debe seguir siendo el primer mecanismo para comandos conocidos, aunque no cubre por
sí solo el objetivo de aprendizaje de integración con IA previsto para v0.3.

### B. Usar un LLM para toda instrucción

Ventaja: un único camino conceptual para interpretar texto.

No se recomienda porque agrega costo, latencia y variabilidad incluso para comandos
exactos que ya funcionan de forma determinista. También aumenta la superficie de
privacidad y los puntos de fallo.

### C. Parser primero y LLM como fallback

Es la opción recomendada:

1. intentar el parser determinista actual;
2. si reconoce el comando, continuar sin red;
3. si no lo reconoce y la integración está habilitada, solicitar una propuesta al
   intérprete de lenguaje natural;
4. validar localmente la propuesta;
5. construir una `Action` usando reglas y catálogo locales;
6. ejecutar mediante el `ActionExecutor` existente.

Este enfoque conserva v0.2 como camino principal y usa IA solo donde aporta valor.

## 5. Flujo propuesto

```text
User command
     |
     v
Deterministic parser --------------------+
     | recognized                        |
     v                                   |
Validated Action                         |
                                         |
     | unsupported                       |
     v                                   |
Natural-language interpreter             |
     |                                   |
     v                                   |
Untrusted ActionProposal                 |
     |                                   |
     v                                   |
Schema + policy + catalog validation     |
     | valid                             |
     v                                   |
Locally constructed Action <-------------+
     |
     v
Existing ActionExecutor
     |
     v
Registered tool
```

La salida del modelo se considera entrada no confiable. Nunca se pasa directamente
al ejecutor.

## 6. Contrato estructurado propuesto

El modelo propondría únicamente intención y destino canónico:

```json
{
  "schema_version": 1,
  "intent": "OPEN_APPLICATION",
  "target": "vscode"
}
```

Valores iniciales permitidos:

| Campo | Valores permitidos |
| --- | --- |
| `schema_version` | `1` |
| `intent` | `OPEN_URL`, `OPEN_APPLICATION`, `UNSUPPORTED` |
| `target` | una clave canónica existente en el catálogo o `null` |

El modelo no debe devolver:

- `tool_name`;
- URL o ruta del ejecutable;
- comandos de shell;
- argumentos libres;
- `RiskLevel` o `requires_confirmation`;
- listas de acciones;
- texto adicional fuera del objeto estructurado.

`confidence` se omite inicialmente: una puntuación autodeclarada por el modelo no
reemplaza la validación local y agregaría una política difícil de calibrar para este
MVP.

## 7. Validación y construcción local

Antes de crear una `Action`, el núcleo deberá comprobar:

1. que la respuesta sea un único objeto válido;
2. que no tenga campos desconocidos;
3. que `schema_version` sea compatible;
4. que `intent` pertenezca al conjunto permitido;
5. que `target` sea coherente con el intent;
6. que el destino exista en el catálogo local;
7. que la combinación se traduzca a una herramienta registrada;
8. que el riesgo y la confirmación sean asignados por código local.

Una respuesta `UNSUPPORTED`, ambigua, incompleta, inválida o fuera del catálogo no
produce una acción.

## 8. Límite entre dominio y proveedor

La arquitectura debe separar dos responsabilidades:

- intérprete de dominio: define el contrato, valida la propuesta y decide si puede
  transformarse en una `Action`;
- adaptador de proveedor: realiza una solicitud y devuelve datos para decodificar.

El dominio no debe importar tipos específicos de un SDK. El adaptador será
reemplazable por un fake en tests y por otra integración en el futuro.

Los nombres y archivos concretos se decidirán durante la implementación para evitar
crear abstracciones antes de comprobar la API elegida.

## 9. Seguridad y fallo seguro

- El modelo no ejecuta herramientas ni decide permisos.
- Texto con apariencia de instrucciones dentro del comando es contenido no confiable;
  no puede cambiar el contrato, la política ni la lista permitida.
- Se permite como máximo una propuesta y una acción por instrucción en v0.3.
- El parser determinista evita llamadas innecesarias.
- Un timeout, error de red, respuesta inválida o destino no permitido termina sin
  ejecutar acciones.
- v0.3 no realiza reintentos automáticos; el usuario puede volver a intentarlo.
- La ausencia de configuración del proveedor no debe romper los comandos de v0.2.
- El texto devuelto por el modelo no debe interpolarse en shell, rutas o logs de error.
- Las defensas del `ActionExecutor` siguen siendo obligatorias aunque la propuesta ya
  haya sido validada.

## 10. Privacidad, configuración y costos

La futura integración debería enviar como máximo el texto de la instrucción necesaria
para interpretarla. No debe adjuntar logs, archivos, variables de entorno, historial,
screenshots ni estado del escritorio.

Antes de enviar texto a un servicio externo deberá existir una decisión explícita
sobre habilitación y privacidad. Las credenciales se obtendrán de variables de
entorno, nunca del código, y no se registrarán.

Por cada interpretación deberían registrarse, sin contenido sensible:

- si se usó el camino determinista o externo;
- proveedor y modelo configurados, si no revelan datos sensibles;
- duración;
- estado: éxito, no soportado, timeout, respuesta inválida o error;
- tokens o costo aproximado cuando el proveedor los informe.

La política inicial propuesta es cero llamadas para comandos deterministas y como
máximo una llamada externa para un comando no reconocido.

## 11. Manejo de errores esperado

| Situación | Resultado seguro |
| --- | --- |
| Integración deshabilitada | Comando no soportado; v0.2 sigue disponible. |
| Credencial ausente | Error de configuración claro, sin revelar valores sensibles. |
| Timeout o red | No crear ni ejecutar una acción. |
| JSON inválido | Rechazar la propuesta. |
| Intent desconocido | Rechazar la propuesta. |
| Destino fuera del catálogo | Rechazar la propuesta. |
| Más de una acción | Rechazar la propuesta completa. |
| Herramienta falla | Mantener el manejo actual del `ActionExecutor`. |

## 12. Estrategia de testing para la futura implementación

La suite predeterminada no dependerá de red ni de una API real. Debería cubrir:

- comandos v0.2 que resuelven sin invocar al proveedor;
- distintas frases que producen propuestas canónicas válidas;
- proveedor deshabilitado o no configurado;
- timeouts y errores simulados;
- JSON inválido, campos extra y versiones desconocidas;
- intents y destinos no permitidos;
- intent incompatible con el destino;
- intent `UNSUPPORTED`;
- rechazo de múltiples acciones y texto adicional;
- construcción local correcta de `Action`, riesgo y herramienta;
- preservación de las barreras del ejecutor;
- logs sin prompt, respuesta completa ni credenciales.

Una prueba real contra un proveedor, si se incorpora, deberá ser opcional, estar
separada de la suite normal y requerir autorización y credenciales del usuario.

## 13. Criterios de aceptación futuros de v0.3

v0.3 podrá considerarse terminada cuando:

- interprete variantes acordadas para capacidades existentes;
- los comandos exactos de v0.2 funcionen sin llamadas externas;
- toda respuesta externa se valide antes de construir una acción;
- ningún resultado pueda introducir herramientas, destinos o argumentos arbitrarios;
- los fallos terminen sin efectos sobre el equipo;
- se documenten proveedor, dependencia, privacidad, configuración y costos;
- la suite de regresión de v0.2 y los tests nuevos estén aprobados;
- las limitaciones se comuniquen y la versión siga siendo demostrable.

## 14. Decisiones pendientes antes de implementar

El usuario deberá revisar y autorizar:

1. proveedor y modelo;
2. SDK oficial o cliente HTTP mínimo;
3. biblioteca estándar o dependencia para validar el esquema;
4. mecanismo explícito para habilitar llamadas externas;
5. nombre de variables de entorno y documentación de configuración;
6. timeout y presupuesto de costo;
7. ejemplos de lenguaje natural que formarán los criterios de aceptación;
8. política para tests opcionales con una API real.

Hasta resolver estas decisiones no debe instalarse un SDK, solicitarse una API key ni
implementarse el adaptador externo.

## 15. Secuencia incremental sugerida

Cuando el usuario autorice implementar v0.3, el trabajo debería dividirse en cambios
pequeños:

1. contrato de propuesta y validación local con tests;
2. intérprete orquestador con proveedor falso;
3. adaptador del proveedor elegido y configuración segura;
4. fallback desde la CLI sin alterar el camino determinista;
5. observabilidad, pruebas de integración locales y documentación;
6. validación final y cierre formal de v0.3.

Cada paso debe conservar una aplicación ejecutable y no habilitar capacidades de
versiones posteriores.
