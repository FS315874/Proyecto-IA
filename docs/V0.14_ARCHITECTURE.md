# Decisión de arquitectura de v0.14

## Resultado

v0.14 deja listo el núcleo para una futura interfaz móvil: pairing explícito,
mensajes autenticados y cifrados, estado acotado, cancelación, confirmaciones remotas,
límites, revocación y una conexión HTTPS solamente saliente. No despliega un relay ni
abre un puerto local.

## Modelo de amenazas

Se consideran un relay curioso o comprometido, manipulación de mensajes, replay,
robo o revocación de un dispositivo, confirmaciones reutilizadas o vencidas, flood de
órdenes y una sesión de Windows bloqueada. No se pretende proteger una computadora ya
comprometida ni reemplazar la seguridad del sistema operativo.

El comportamiento seguro es rechazar sin efecto y sin revelar detalles. Un sobre no
auténtico no consume la secuencia; uno auténtico consume de forma persistente su ID y
secuencia antes de producir cualquier efecto. Una sesión local suspendida conserva la
decisión de v0.12: no acepta tareas hasta reanudación manual.

## Alternativas evaluadas

| Alternativa | Decisión |
| --- | --- |
| Socket o servidor HTTP en la PC | Descartado: expone superficie entrante y complica red doméstica. |
| TLS hasta un relay con contenido en claro | Descartado: el relay podría leer o alterar órdenes. |
| Criptografía propia | Descartado: riesgo innecesario de diseño e implementación. |
| Relay HTTPS saliente más AES-GCM E2E | Elegido: no abre puertos y el relay sólo ve sobres. |

Se agregó `cryptography==50.0.0` porque la biblioteca estándar no ofrece una primitiva
AEAD moderna. Se usa AES-256-GCM y HKDF-SHA256; no se implementan algoritmos propios.
La versión fijada requiere Python 3.9 o posterior, publica wheels para Windows/Python
3.13 y declara licencia Apache-2.0 o BSD-3-Clause.

## Pairing y almacenamiento

`DeviceRegistry.begin_pairing` genera un ID y 32 bytes aleatorios. El secreto se
entrega una vez para transferirlo fuera de banda. El teléfono demuestra posesión con
HMAC-SHA256 ligado al ID y el usuario debe aprobar localmente antes de activar el
registro. El intento vence a los cinco minutos.

El JSON se guarda de forma atómica fuera del repositorio, por defecto en
`%LOCALAPPDATA%\DesktopAgent\devices.json`. Sólo contiene el secreto protegido para el
usuario actual mediante Windows DPAPI, nunca su forma en claro ni la prueba. Revocar
borra el blob protegido y los IDs recientes.

## Protocolo y privacidad

HKDF deriva una clave por dispositivo y dirección para impedir reflexión entre
cliente y agente. Cada sobre lleva versión, dispositivo, ID único, secuencia, fecha,
nonce y ciphertext. La metadata completa y la dirección son AAD de AES-GCM. Se
validan esquema exacto, longitudes, tipos y tamaños antes de usar datos.

El relay ID es un identificador público de ruteo, no un secreto. URLs, headers y logs
no contienen claves. El desafío de confirmación es efímero y viaja sólo dentro del
ciphertext. Los resúmenes remotos no incluyen orden, etiqueta, resultado ni evidencia
privada; muestran como máximo ID, estado y herramienta de veinte tareas.

## Separación de responsabilidades

```text
teléfono futuro
  -> sobre AES-GCM
  -> relay HTTPS opaco
  -> cliente saliente manual
  -> RemoteGateway
  -> DesktopAgentService
  -> parser / catálogo / política / ActionExecutor
  -> herramienta registrada
```

El gateway nunca invoca una herramienta. `COMMAND` llama a `submit`; `CANCEL` opera
sobre un ID; `STATUS` crea un resumen; `CONFIRMATION` construye una decisión de canal
remoto sólo después de verificar los cuatro campos exactos y que la solicitud lo
admita. Una orden de texto como `sí` sigue siendo una orden normal y no confirma.

## Límites y ciclo de vida

- diez órdenes por minuto y tres tareas pendientes por dispositivo;
- mensajes con hasta 500 caracteres, plaintext de 8 KiB y ciphertext de 16 KiB;
- reloj con tolerancia de 60 segundos, secuencia creciente e historial de 64 IDs;
- transporte TLS verificado, puerto 443, paths fijos, timeout y respuesta de 32 KiB;
- worker sin autostart, cancelable y con estados offline, connecting, online, error y
  stopped.

## Validación y límites conocidos

Treinta y dos pruebas verifican round-trip, separación direccional, ciphertext
alterado, secretos en comandos, esquema, pairing, expiración, DPAPI real, persistencia
de secuencias, replay, revocación, rate limit, confirmación exacta, redacción, paths
HTTPS y ciclo del worker. `python -m scripts.remote14_qa_check` recorre una orden y una
confirmación cifradas sobre `DesktopAgentService`, rechaza el replay y valida la
revocación sin red ni efectos reales.

No existen todavía aplicación móvil, servidor relay, recuperación de dispositivo,
notificaciones push ni UI de pairing. Activar un relay real requerirá elegir proveedor,
credenciales, despliegue, política de retención, revisión de privacidad y pruebas
externas autorizadas. El proyecto no afirma que una integración real haya sido
probada.
