## 1. Objetivo

v0.3 permitiría interpretar variantes de lenguaje natural para las capacidades que
el agente ya tenga autorizadas. Por ejemplo:

```text
poneme youtube
iniciá el editor de código
quiero usar la calculadora
```

El resultado seguiría siendo una única acción explícita y validada. Esta versión no
amplía qué puede hacer el equipo; solo propone una forma más flexible de seleccionar
acciones existentes.

## 2. Estado de partida comprobado

v0.2 usa un flujo completamente determinista:

```text
CLI -> parse_command -> Action -> ActionExecutor -> herramienta registrada
```

El repositorio ya contiene:

- `Action`, `Intent`, `RiskLevel` y `requires_confirmation`;
- un catálogo cerrado de sitios y aplicaciones;
- las herramientas `open_url` y `open_application`;
- un ejecutor que rechaza riesgos no seguros y herramientas desconocidas;
- dependencias inyectables para probar efectos sin abrir aplicaciones reales;
- una suite basada en `unittest`, con efectos y cliente externo reemplazables.

Estas fronteras se conservan. El intérprete no reemplaza al ejecutor, al catálogo ni
a las validaciones existentes.

## 3. Alcance propuesto

v0.3 incluye solamente:

- interpretación de expresiones alternativas para intents existentes;
- salida estructurada de una sola propuesta;
- validación local de estructura, intent y destino;
- fallback al mensaje de comando no soportado ante cualquier ambigüedad o fallo;
- métricas básicas de uso, duración y resultado de la interpretación;
- pruebas con un proveedor falso, sin llamadas reales en la suite predeterminada.

Queda fuera:

- agregar herramientas o destinos por decisión del modelo;
- URLs, ejecutables, rutas o argumentos arbitrarios;
- planes o tareas de varios pasos;
- reintentos autónomos;
- Playwright, screenshots, visión, mouse o teclado;
- memoria, persistencia o envío de contexto del escritorio;
- selección automática de acciones `CAUTION` o `DANGEROUS`;
- confirmación de acciones sensibles;
- una prueba contra la API real.

## 4. Opciones consideradas

### A. Ampliar únicamente el parser determinista

Ventajas:

- sin costo, red ni dependencia externa;
- comportamiento rápido, privado y reproducible;
- pruebas sencillas.

Limitaciones:

- cada nueva formulación requiere reglas o alias;
- escala mal ante expresiones ambiguas o variadas.

Debe seguir siendo el primer mecanismo para comandos conocidos, aunque no cubre por
sí solo el objetivo de aprendizaje de integración con IA previsto para v0.3.

### B. Usar un LLM para toda instrucción

Ventaja: un único camino conceptual para interpretar texto.

No se recomienda porque agrega costo, latencia y variabilidad incluso para comandos
exactos que ya funcionan de forma determinista. También aumenta la superficie de
privacidad y los puntos de fallo.

### C. Parser primero y LLM como fallback

Es la opción recomendada:

1. intentar el parser determinista actual;
2. si reconoce el comando, continuar sin red;
3. si no lo reconoce y la integración está habilitada, solicitar una propuesta al
   intérprete de lenguaje natural;
4. validar localmente la propuesta;
5. construir una `Action` usando reglas y catálogo locales;
6. ejecutar mediante el `ActionExecutor` existente.

Este enfoque conserva v0.2 como camino principal y usa IA solo donde aporta valor.

## 5. Flujo propuesto

```text
User command
     |
     v
Deterministic parser --------------------+
     | recognized                        |
     v                                   |
Validated Action                         |
                                         |
     | unsupported                       |
     v                                   |
Natural-language interpreter             |
     |                                   |
     v                                   |
Untrusted ActionProposal                 |
     |                                   |
     v                                   |
Schema + policy + catalog validation     |
     | valid                             |
     v                                   |
Locally constructed Action <-------------+
     |
     v
Existing ActionExecutor
     |
     v
Registered tool
```

La salida del modelo se considera entrada no confiable. Nunca se pasa directamente
al ejecutor.

## 6. Contrato estructurado propuesto

El modelo propondría únicamente intención y destino canónico:

```json
{
  "schema_version": 1,
  "intent": "OPEN_APPLICATION",
  "target": "vscode"
}
```

Valores iniciales permitidos:

| Campo | Valores permitidos |
| --- | --- |
| `schema_version` | `1` |
| `intent` | `OPEN_URL`, `OPEN_APPLICATION`, `UNSUPPORTED` |
| `target` | una clave canónica existente en el catálogo o `null` |

El modelo no debe devolver:

- `tool_name`;
- URL o ruta del ejecutable;
- comandos de shell;
- argumentos libres;
- `RiskLevel` o `requires_confirmation`;
- listas de acciones;
- texto adicional fuera del objeto estructurado.

`confidence` se omite inicialmente: una puntuación autodeclarada por el modelo no
reemplaza la validación local y agregaría una política difícil de calibrar para este
MVP.

## 7. Validación y construcción local

Antes de crear una `Action`, el núcleo deberá comprobar:

1. que la respuesta sea un único objeto válido;
2. que no tenga campos desconocidos;
3. que `schema_version` sea compatible;
4. que `intent` pertenezca al conjunto permitido;
5. que `target` sea coherente con el intent;
6. que el destino exista en el catálogo local;
7. que la combinación se traduzca a una herramienta registrada;
8. que el riesgo y la confirmación sean asignados por código local.

Una respuesta `UNSUPPORTED`, ambigua, incompleta, inválida o fuera del catálogo no
produce una acción.

## 8. Límite entre dominio y proveedor

La arquitectura debe separar dos responsabilidades:

- intérprete de dominio: define el contrato, valida la propuesta y decide si puede
  transformarse en una `Action`;
- adaptador de proveedor: realiza una solicitud y devuelve datos para decodificar.

El dominio no debe importar tipos específicos de un SDK. El adaptador será
reemplazable por un fake en tests y por otra integración en el futuro.

El primer incremento concentra estas responsabilidades relacionadas en
`desktop_agent/interpretation.py`. La interfaz `ProposalProvider` devuelve `object`
para mantener explícito que sus datos no son confiables y no importa tipos de ningún
SDK.

NLI-05 implementó `desktop_agent/openai_provider.py`. El módulo usa una interfaz mínima
inyectable para `responses.create`, construye el JSON Schema localmente y devuelve el
JSON decodificado sin crear una `Action`. El SDK solo se importa al construir el
cliente real, cuya creación NLI-06 difiere hasta la primera propuesta externa; el
dominio continúa sin conocer sus tipos. Cada orden externa se limita a 1.000
caracteres y cada salida a 128 tokens.

## 9. Seguridad y fallo seguro

- El modelo no ejecuta herramientas ni decide permisos.
- Texto con apariencia de instrucciones dentro del comando es contenido no confiable;
  no puede cambiar el contrato, la política ni la lista permitida.
- Se permite como máximo una propuesta y una acción por instrucción en v0.3.
- El parser determinista evita llamadas innecesarias.
- Un timeout, error de red, respuesta inválida o destino no permitido termina sin
  ejecutar acciones.
- v0.3 no realiza reintentos automáticos; el usuario puede volver a intentarlo.
- La ausencia de configuración del proveedor no debe romper los comandos de v0.2.
- El texto devuelto por el modelo no debe interpolarse en shell, rutas o logs de error.
- Las defensas del `ActionExecutor` siguen siendo obligatorias aunque la propuesta ya
  haya sido validada.

## 10. Privacidad, configuración y costos

La integración aprobada enviará como máximo el texto de la instrucción necesaria para
interpretarla, la instrucción mínima de clasificación, las claves canónicas del
catálogo y el esquema JSON de la propuesta. No debe adjuntar logs, archivos, variables
de entorno, historial, screenshots, rutas, contenido de ventanas ni estado adicional
del escritorio.

La decisión NLI-03 del 2026-08-24 seleccionó OpenAI Responses API,
`gpt-5.6-luna` con razonamiento `none`, Structured Outputs y el SDK oficial de Python.
La integración permanecerá deshabilitada por defecto, usará `store=false` y solicitudes
independientes, y obtendrá la credencial exclusivamente desde `OPENAI_API_KEY`, nunca
desde el código ni los logs.

NLI-04 implementó `desktop_agent/provider_config.py` sin importar ni instalar ese SDK.
`DESKTOP_AGENT_AI_ENABLED` acepta un opt-in booleano y vale falso si está ausente;
`DESKTOP_AGENT_AI_TIMEOUT_SECONDS` vale 5 segundos por defecto y solo admite valores
finitos mayores que 0 y de hasta 30 segundos.
`DESKTOP_AGENT_AI_MONTHLY_BUDGET_USD` vale USD 1,00 por defecto y admite valores
entre USD 0,01 y USD 1.000. `OPENAI_API_KEY` se exige únicamente al habilitar la
integración. Si está deshabilitada, la configuración específica se ignora y la
credencial no se conserva. Los errores identifican la variable afectada sin repetir
su valor y la representación de `ProviderConfig` omite la credencial.

El SDK oficial se eligió frente a un cliente HTTP propio para reducir código de
autenticación, transporte y manejo de respuestas. NLI-05 fijó `openai==3.3.1`, cuya
metadata declara Python 3.10 o posterior y licencia Apache-2.0. La resolución observada
incluyó 13 paquetes transitivos con licencias permisivas declaradas. Los tipos del SDK
no atraviesan el límite `ProposalProvider`.

Por cada interpretación se registran, sin contenido sensible:

- si se usó el camino determinista o externo;
- proveedor y modelo configurados, si no revelan datos sensibles;
- duración;
- estado: éxito, no soportado, respuesta inválida, presupuesto agotado, fallo de
  registro o error del proveedor;
- tokens y costo aproximado de la solicitud cuando el proveedor los informe;
- mes, solicitudes, tokens, costo estimado acumulado, límite, saldo, solicitudes sin
  medición y reservas pendientes.

`InterpretationResult` conserva esa metadata sin almacenar la orden ni la respuesta.
`interpret()` sigue devolviendo `Action | None` como fachada compatible y
`interpret_detailed()` expone el resultado observable a la CLI. Los estados actuales
son `success`, `unsupported`, `provider_error`, `invalid_proposal`,
`budget_exceeded` y `usage_tracking_error`.

El adaptador acepta únicamente contadores de uso enteros, no negativos y coherentes.
Si una respuesta llegó pero no produjo una propuesta válida, el error tipado conserva
solo esa telemetría numérica para no perder el costo incurrido.
Para `gpt-5.6-luna` estima el costo con las tarifas consultadas el 2026-08-24:
USD 0,20 por millón de tokens de entrada, USD 0,02 por entrada cacheada, USD 0,25 por
escritura de caché y USD 1,20 por salida. Esa cifra es orientativa y debe revalidarse
antes de uso real.

NLI-07A agregó `MonthlyUsageLedger` y `BudgetedProposalProvider`. El registro conserva
historial por mes calendario local en
`%LOCALAPPDATA%\DesktopAgent\ai_usage.json` o, si esa variable no está disponible,
`~/.desktop_agent/ai_usage.json`. Solo guarda contadores numéricos, costo estimado y
reservas; excluye orden, respuesta, credencial y contenido del escritorio. El límite
mensual es configuración, no se guarda dentro del historial, por lo que puede cambiar
sin borrar consumos anteriores.

Antes de contactar al proveedor se persiste una reserva de USD 0,01. Al finalizar se
reemplaza por el costo estimado a partir de `response.usage`; si no hay telemetría, la
reserva completa se contabiliza de forma conservadora. Una reserva pendiente sobrevive
un cierre inesperado. Un archivo ausente empieza vacío; un archivo corrupto,
inaccesible o no actualizable bloquea el fallback. Este límite es local y aproximado:
no sustituye el panel de facturación de OpenAI y presupone una única instancia activa.

La política inicial aprobada es cero llamadas para comandos deterministas y como
máximo una llamada externa, sin reintentos automáticos, para un comando no reconocido.
El timeout objetivo inicial es de 5 segundos y todo fallo termina sin acción.

Como referencia consultada el 2026-08-24, el modelo cuesta USD 0,20 por millón de
tokens de entrada y USD 1,20 por millón de tokens de salida. OpenAI declara que los
datos enviados por API no se usan para entrenamiento salvo participación voluntaria;
los registros de monitoreo pueden retener contenido hasta 30 días bajo la configuración
predeterminada. Una prueba real seguirá requiriendo un presupuesto y autorización.

## 11. Manejo de errores esperado

| Situación | Resultado seguro |
| --- | --- |
| Integración deshabilitada | Comando no soportado; v0.2 sigue disponible. |
| Credencial ausente | Error de configuración claro, sin revelar valores sensibles. |
| Presupuesto mensual sin reserva disponible | No contactar al proveedor. |
| Registro de uso corrupto o inaccesible | Bloquear el fallback sin ejecutar acción. |
| Timeout o red | No crear ni ejecutar una acción. |
| JSON inválido | Rechazar la propuesta. |
| Intent desconocido | Rechazar la propuesta. |
| Destino fuera del catálogo | Rechazar la propuesta. |
| Más de una acción | Rechazar la propuesta completa. |
| Herramienta falla | Mantener el manejo actual del `ActionExecutor`. |

## 12. Estrategia de testing

La suite predeterminada no dependerá de red ni de una API real. Debería cubrir:

- comandos v0.2 que resuelven sin invocar al proveedor;
- distintas frases que producen propuestas canónicas válidas;
- proveedor deshabilitado o no configurado;
- timeouts y errores simulados;
- JSON inválido, campos extra y versiones desconocidas;
- intents y destinos no permitidos;
- intent incompatible con el destino;
- intent `UNSUPPORTED`;
- rechazo de múltiples acciones y texto adicional;
- construcción local correcta de `Action`, riesgo y herramienta;
- preservación de las barreras del ejecutor;
- logs sin prompt, respuesta completa ni credenciales.

Una prueba real contra un proveedor, si se incorpora, deberá ser opcional, estar
separada de la suite normal y requerir autorización y credenciales del usuario.
NLI-07A dejó aprobadas 74 pruebas locales: incluyen el comando exacto sin invocar al
proveedor, el fallback válido desde la CLI, la configuración inválida, el fallo
externo sin ejecución de herramientas, todos los estados de interpretación y la
ausencia de prompt, respuesta y credencial en el log. También cubren acumulación,
persistencia, cambio de mes, reservas pendientes, bloqueo previo y archivo corrupto.
NLI-08 agregó seis pruebas de aceptación simulada; la suite de cierre contiene 80
pruebas locales.

## 13. Criterios de aceptación de v0.3

NLI-08 comprobó estos criterios mediante simulación:

- interprete variantes acordadas para capacidades existentes;
- los comandos exactos de v0.2 funcionen sin llamadas externas;
- toda respuesta externa se valide antes de construir una acción;
- ningún resultado pueda introducir herramientas, destinos o argumentos arbitrarios;
- los fallos terminen sin efectos sobre el equipo;
- se documenten proveedor, dependencia, privacidad, configuración y costos;
- la suite de regresión de v0.2 y los tests nuevos estén aprobados;
- las limitaciones se comuniquen y la versión siga siendo demostrable.

## 14. Decisiones y permisos

El usuario aprobó la opción A el 2026-08-24: OpenAI, `gpt-5.6-luna`, Responses API,
Structured Outputs, SDK oficial de Python, habilitación explícita y credencial desde
entorno. También aprobó el límite de una llamada sin reintentos, el timeout objetivo de
5 segundos, la minimización de datos y el fallo seguro. El 2026-08-24 pidió además un
conteo persistente de tokens y dinero con límite mensual modificable, inicialmente
fijado en USD 1,00.

El usuario autorizó el 2026-08-24 agregar `openai==3.3.1` y descargarlo temporalmente
para pruebas sin red. Esa autorización se usó para comprobar la firma del SDK y el
adaptador con la operación externa reemplazada por un mock. No autorizó crear o guardar
una API key ni realizar una llamada real. Ese día eligió una aceptación simulada con
`abrir youtube`, `poneme YouTube`, `quiero hacer una cuenta en la calculadora`,
`abrime el editor Visual Studio Code` y `abrime Spotify`, además de los escenarios de
proveedor deshabilitado, fallo y presupuesto. Cualquier test real seguirá siendo
opcional, separado de la suite normal y expresamente autorizado.
