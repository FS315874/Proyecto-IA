# v0.20 — Volumen por dispositivo de salida

## Alcance

Esta versión agrega una sola capacidad: establecer y comprobar el volumen maestro de
una salida de audio activa de Windows identificada por su nombre. Ejemplos:

```text
Poné el volumen de HyperX al 35 %.
Poné el volumen de los altavoces de mis auriculares HyperX al nivel de 35 %.
```

No cambia la salida predeterminada, el estado de silencio, el volumen de Spotify ni
los controles internos de VoiceMeeter. El límite inicial es de 0 a 80 % para evitar
que una interpretación equivocada produzca un nivel extremo. Los valores mayores se
rechazan antes de tocar Windows; una política confirmable para niveles superiores es
una decisión futura.

## Arquitectura

El parser determinista acepta el dispositivo como dato y construye
`set_output_volume(device, percent)`. El proveedor de IA puede proponer el mismo
intent mediante un objeto cerrado `{device, percent}`; no propone identificadores de
endpoint, código ni comandos. Los planes usan el mismo contrato. Toda acción pasa por
`ActionExecutor` con `Intent.SYSTEM_CHANGE`, `RiskLevel.SAFE` y argumentos de texto
validados localmente.

`OutputVolumeTool` enumera únicamente endpoints de reproducción activos. Primero
busca el nombre completo normalizado; después exige que las palabras específicas
del pedido aparezcan en un único nombre. Palabras conversacionales como «los
altavoces de mis auriculares» no obligan a memorizar la etiqueta exacta. Cero
coincidencias falla; más de una también falla y solicita un nombre más completo.
Nunca elige la primera salida.

`WindowsCoreAudioBackend` usa las interfaces oficiales MMDevice e
`IAudioEndpointVolume` mediante `ctypes`, incluido en Python. No ejecuta PowerShell,
shell, selectores, mouse o teclado y no agrega dependencias de producción. El backend
es inyectable: las pruebas usan endpoints ficticios y no cambian el equipo.

## Verificación, privacidad y observabilidad

Después de `SetMasterVolumeLevelScalar`, el backend llama
`GetMasterVolumeLevelScalar`. La herramienta sólo informa éxito si la diferencia
respecto del valor solicitado es como máximo 1,1 puntos porcentuales. Un HRESULT
exitoso sin lectura posterior no basta.

La CLI `python -m desktop_agent --audio-outputs` lista sólo nombres amigables; no
muestra identificadores internos. Los logs e incidentes no guardan el nombre pedido,
el identificador ni el porcentaje. Los códigos cerrados distinguen backend no
disponible, entrada inválida, salida ausente, ambigua y volumen no confirmado.

La enumeración y lectura reales del 2026-09-19 comprobaron Core Audio, detectaron una
salida HyperX y múltiples endpoints VoiceMeeter, y leyeron el volumen actual de
HyperX sin cambiarlo. El runner
`python -m scripts.audio20_qa_check` usa dobles y no produce efectos reales. La
regresión cerró con **119 pruebas específicas, 547 Python y 13 JavaScript**. El
2026-09-24 el usuario pidió 35 % sobre HyperX y confirmó que el recorrido funcionó
correctamente. Con esa observación quedó aceptado el cambio real sobre la salida
física; la herramienta no ejecuta ninguna operación de mute.

## Límites

- Sólo Windows y endpoints de reproducción activos.
- No se elige una salida entre coincidencias ambiguas.
- No se controlan buses o tiras internas de VoiceMeeter; se ven sus endpoints de
  Windows, que pueden tener nombres muy parecidos y exigir el nombre completo.
- No se cambia mute ni dispositivo predeterminado.
- No se aceptan niveles superiores a 80 % en esta versión.
- La prueba automatizada no sustituye la confirmación humana de la salida física ni
  de la intensidad audible; esa aceptación personal quedó registrada el 2026-09-24.
